# DDoS и Incident Response Runbook

Дата актуализации: 2026-11-08. Production: хостинг Beget.

## 1. Контакты и полномочия

Заполнить до релиза и хранить копию вне сайта:

| Роль | Имя/канал | Полномочия |
| --- | --- | --- |
| Incident Commander | TODO | объявляет инцидент, принимает решение о блокировках/откате |
| Владелец Beget | TODO | DNS, TLS, WAF/anti-DDoS, логи, backup/restore, поддержка |
| Администратор Bitrix | TODO | пользователи, MFA, модули, event log, maintenance |
| Разработчик | TODO | анализ кода, hotfix, тесты |
| Владелец домена/почты | TODO | DNS, SPF/DKIM/DMARC, почтовая репутация |
| Коммуникации | TODO | статус клиентам и заказчику |

Никто не публикует пароли, `.env`, SQL dump, cookies, полный request body или
персональные данные в чатах и тикетах.

## 2. Классификация

| Уровень | Пример | Время реакции |
| --- | --- | --- |
| SEV-1 | сайт/формы недоступны, активная компрометация, массовая утечка | немедленно, эскалация Beget |
| SEV-2 | частичная недоступность, подтверждённый захват учётной записи, спам форм | до 30 минут |
| SEV-3 | подозрительная активность без влияния, уязвимая зависимость | рабочий день |
| SEV-4 | hardening/наблюдение | по плану |

## 3. Первые 15 минут

1. Назначить Incident Commander, время начала и severity.
2. Зафиксировать симптомы: URL, время UTC/MSK, HTTP status, screenshot,
   request ID/IP/UA только при наличии законного доступа.
3. Проверить Beget status/support, DNS и сертификат; не выполнять DDoS-нагрузку.
4. Сохранить копии access/error/event logs и хеши файлов вне webroot.
5. Не удалять логи и не «лечить» сервер до фиксации доказательств.
6. При компрометации учётной записи: завершить сессии, заблокировать пользователя,
   сменить пароль и второй фактор с доверенного устройства.
7. При утечке секрета: сначала отозвать/заменить секрет, затем исправлять код.

## 4. DDoS/DoS playbook

### 4.1 Диагностика без усиления атаки

- определить: DNS/TLS timeout, network saturation, 429/5xx, PHP workers, DB,
  конкретный endpoint или bot-spam;
- сравнить нормальный baseline RPS/latency/размер запроса с периодом атаки;
- выделить URI, методы, ASN/IP, User-Agent, сессии и объём upload;
- проверить состояние SMTP queue и MySQL slow queries.

### 4.2 Edge/Beget

Через поддержку/панель Beget:

1. включить доступную anti-DDoS/WAF/bot-защиту;
2. применить временный rate limit к атакуемому URI/методу;
3. заблокировать подтверждённые источники/ASN/страны только с оценкой ложных
   срабатываний;
4. включить challenge для анонимных форм, не блокируя поисковых роботов вслепую;
5. запросить сохранение edge-логов и точное время начала/окончания;
6. при необходимости временно отключить только дорогой endpoint, а не весь сайт.

В production нет Docker/Caddy, поэтому команды контейнеров из локального
окружения к Beget не применяются.

### 4.3 Уровень приложения

- формы/CAPTCHA/AJAX: POST + CSRF, session/IP quotas, 429 + `Retry-After`;
- ограничить размер тела, число файлов, время выполнения и частоту отправки;
- включить Bitrix proactive protection/activity control после проверки в staging;
- для атакуемой формы временно выключить email side effect или поставить очередь;
- кэшировать безопасные публичные GET, но не auth/cart/admin/form responses;
- не добавлять блокировки по одному только `Referer`/User-Agent.

### 4.4 Критерии стабилизации

- 2xx/3xx и latency вернулись к baseline не менее чем на 30 минут;
- нет роста 5xx, PHP/DB saturation и SMTP queue;
- временные правила задокументированы с владельцем и сроком снятия;
- доказательства и временная шкала сохранены.

## 5. Компрометация приложения

1. Перевести сайт в controlled maintenance только при необходимости.
2. Снять forensic-копии журналов, изменённых файлов и списка пользователей.
3. Сравнить код с доверенным Git commit; не использовать `git reset --hard` до
   сохранения доказательств.
4. Проверить новые админ-учётки, сессии, cron/agents, `.htaccess`, PHP-файлы в
   `upload/`, изменённые настройки и почтовые шаблоны.
5. Отозвать сессии/пароли/API tokens/SMTP credentials по степени риска.
6. Восстановить из проверенного backup или развернуть чистую версию.
7. Обновить Bitrix/модули, применить hotfix, повторить security/smoke тесты.
8. Уведомить затронутых лиц и регулятора, если это требуется законом/договором.

## 6. Утечка секрета

1. Считать секрет скомпрометированным, даже если файл быстро удалён из Git.
2. Отозвать секрет у провайдера; создать новый с минимальными правами.
3. Обновить секрет только в защищённой конфигурации Beget/окружении.
4. Проверить audit log провайдера с момента первого появления секрета.
5. Удалить секрет из текущего кода; очистку Git history выполнять отдельным
   согласованным окном, предупредив всех разработчиков о re-clone.
6. Запустить повторный secret scan и добавить правило предотвращения.

## 7. Безопасные диагностические команды

Локально, из корня проекта:

```bash
npm run test:security
npm run audit:security:config
npm audit
git diff --check
```

Пассивно для production (без нагрузки):

```bash
curl -I --max-time 15 https://ral-master.ru/
```

Журналы Beget получать через штатную панель/поддержку. Не копировать в Git.

## 8. Восстановление и приёмка

- проверить DNS, TLS, HTTP headers, главную, каталог, корзину, формы и admin login;
- проверить, что секреты и backup-файлы недоступны по HTTP;
- выполнить security suite и полный функциональный smoke в staging/production-safe
  режиме;
- проверить mail delivery тестовым адресатом без рассылки клиентам;
- снять временные правила только после анализа причины;
- оформить postmortem не позднее 3 рабочих дней.

## 9. Postmortem

Обязательные поля: timeline, impact, affected data/users, root cause, detection
gap, response quality, что сработало/не сработало, корректирующие действия,
владелец и срок. Формулировки должны описывать системные причины, а не вину
конкретного человека.

## 10. Регулярная готовность

- ежемесячно: review администраторов/MFA/event log, secret scan, restore sample;
- ежеквартально: tabletop SEV-1/DDoS, проверка контактов Beget и лимитов;
- перед релизом: обновления Bitrix/Aspro, security regression, backup + restore
  evidence;
- после изменения форм/upload/auth: обновить threat model и тесты.
