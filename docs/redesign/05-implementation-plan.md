# План реализации редизайна

План построен с обязательными quality gates. Переход к следующей итерации запрещён при наличии новой критической регрессии в текущей.

## Gate 0 — безопасность и контроль изменений

- Первичная инфраструктурная точка сохранена коммитом `c345081...`; фактический baseline полного редизайна — `a43ff3e...`.
- Ветка `feature/full-paper-redesign` создана локально.
- Секреты, Bitrix core, upload/cache/runtime-данные и тестовые артефакты исключены из Git.
- Production-инфраструктура не изменяется.

## Gate 1 — воспроизводимый runtime и baseline

1. Восстановить Docker Desktop/WSL.
2. Импортировать санитизированную БД.
3. Проверить `docker compose up --build`, healthcheck и главную страницу.
4. Выполнить production-like сборку.
5. Запустить полный Playwright baseline локально.
6. Проверить state-changing сценарии только на изолированных данных.

До прохождения Gate 1 изменения UI не должны начинаться: иначе невозможно отличить исходный дефект от регрессии.

## Предлагаемая архитектура UI

- Не изменять закрытые/обфусцированные файлы Bitrix и vendor.
- Реализовывать дизайн в `local/` через собственный шаблон/дочерний слой и component templates; конкретный способ переключения шаблона подтвердить на локальной БД.
- Ввести CSS custom properties для извлечённых цветов, типографики, spacing, radii и контейнеров.
- Подключать `Inter Tight` и `Onest` с проверкой лицензии, preload и font-display; `Manrope` — только где подтверждено макетом.
- Сохранить серверные endpoints, маршруты и Bitrix-компоненты; менять presentation layer по возможности отдельно от бизнес-логики.
- Использовать семантическую разметку, keyboard navigation, видимый focus, корректные labels/errors и reduced motion.
- Не копировать staging/production-секреты в `.env`, код или Git.

## Последовательность продуктовых итераций

1. Foundations: tokens, fonts, reset, containers, buttons, inputs, cards, базовые states.
2. Shell: header, navigation, footer, breadcrumbs, mobile drawer.
3. Главная страница.
4. Продукция и общие listing/detail patterns.
5. Металлообработка и порошковая окраска.
6. Производство/компания.
7. Проекты listing/detail, включая «ЖК Символ».
8. Контакты.
9. Формы и modal flows.
10. Калькуляторы после утверждения бизнес-правил.
11. Производные страницы без отдельных Paper-фреймов.
12. Полная функциональная, accessibility и визуальная регрессия.

## Цикл каждой итерации

1. Обновить статус и scope в `ITERATIONS.md`.
2. Реализовать минимальный законченный вертикальный срез.
3. Собрать production-like вариант.
4. Проверить фактический запуск.
5. Выполнить относящиеся автотесты.
6. Снять screenshots на заданных viewport.
7. Сравнить с Paper и проверить responsive/interactions.
8. Исправить дефекты и повторить проверки.
9. Записать фактический результат, дефекты и ограничения.
10. Обновить `PROGRESS.md`, `TEST_RESULTS.md` и `VISUAL_QA.md`.

## Критерии окончательной готовности

- Docker dev и production-like profiles реально собираются и запускаются.
- Ключевые маршруты и сценарии работают на локальной изолированной БД.
- Нет новых критических/высоких функциональных и accessibility-регрессий.
- Целевые desktop screenshots соответствуют Paper в согласованном допуске.
- Адаптив проверен на mobile/tablet/desktop, несмотря на отсутствие mobile Paper-фреймов.
- Формы, поиск, навигация, проекты, каталог и optional flows проверены.
- Все известные ограничения перечислены, итоговый отчёт заполнен фактическими результатами.
